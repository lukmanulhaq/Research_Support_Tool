Latency-First Sub-tasks

Router & Retriever are assigned the fastest possible options (8B LLM + FAISS) so they never bottleneck the expensive reasoning steps.

Reasoning-First Sub-tasks

Synthesizer uses DeepSeek R1 (chain-of-thought, o1-class) because synthesis quality gates the final academic output. Cost of latency is justified.

Cross-Provider Critique

Critic uses Google Gemini (not DeepSeek) to eliminate provider self-affirmation bias. The 1M context window is a unique advantage for full-document critique.

Agentic Design Patterns Used

  • Orchestrator-Worker: The Orchestrator agent receives the raw query, decomposes it into a JSON task plan, and delegates execution to the Router/Workers.
  • ReAct (Reasoning + Acting): The Retriever agent operates in a ReAct loop. It emits a Thought (e.g., "query confidence is low"), executes an Action (FAISS vector search tool), and processes the Observation (top-k chunks).
  • Reflection & Self-Critique: The Critic agent acts as a guardrail. It receives the draft synthesis alongside the grounded evidence chunks, scores the draft for hallucinations (0-10), and explicitly approves or corrects it.

Common Viva Defense Points

  • Why not just use a single LLM for everything?

    A single model suffers from context dilution and instruction amnesia. By splitting routing, reasoning, and critique across specialized agents with dedicated system prompts, we enforce strict academic boundaries and mitigate hallucinations.

  • How is Agent-to-Agent (A2A) communication handled?

    Agents communicate synchronously by passing structured JSON payloads. The global state is managed natively via st.session_state, creating an immutable append-only trace log that the frontend parses for the A2A Trace tab.

  • Why FAISS over a dedicated vector database like Pinecone?

    For a 24-paper corpus, a local FAISS index running in-memory via FlatIP (Inner Product/Cosine) is significantly faster (<10ms latency) and cheaper than the network overhead of querying a cloud vector database.
